= Lab 1.5 — Explore the Developer Template

The template repository is already initialized and published on GitHub at
https://github.com/fjcloud/go-app-template[fjcloud/go-app-template].
Your role as Platform Engineer is to understand what it contains, why each file is there,
and how to adapt `GIT_SERVER` in the template before sharing the launch URL with developers.

[NOTE]
====
*Estimated time:* 15 minutes +
*Persona:* Platform Engineer +
*Deliverable:* Understanding of the template + participant DevSpaces URL ready to share
====

== What is in the template?

[source,sh,role=execute]
----
git clone https://github.com/fjcloud/go-app-template
cd go-app-template
ls -la
----

You should see:

[source,console]
----
AGENTS.md          ← platform conventions read by OpenCode
devfile.yaml       ← workspace definition (gitpop + Ansible + one-click tasks)
deploy/base/       ← Kustomize: Deployment, Service, Route
pipeline/base/     ← Kustomize: Tekton Pipeline + PVC
gitops/base/       ← Kustomize: developer-owned ArgoCD instance
scripts/
  git-push.yml     ← Ansible: push code to personal Git repo
  build-image.yml  ← Ansible: Tekton PipelineRun (git-clone + buildah)
  gitops-deploy.yml← Ansible: ArgoCD instance + Application sync
----

The key boundary:

* OpenCode generates *code* (`main.go`, `go.mod`, `Dockerfile`) guided by `AGENTS.md`
* The Ansible playbooks handle all *platform operations* — each task is named and readable
* Kustomize manifests are applied by the playbooks via `oc apply -k`

== Step 1: Read AGENTS.md

`AGENTS.md` is the file OpenCode reads before *every* session. It defines what the LLM
must generate, what already exists, and how to trigger the deploy pipeline.

[source,sh,role=execute]
----
cat AGENTS.md
----

Read through it carefully. Notice:

* *Files YOU must generate* — `main.go`, `go.mod`, `Dockerfile` with an exact two-stage template
* *Files already in the repository* — the LLM must NOT touch `deploy/`, `pipeline/`, `gitops/`, `scripts/`
* *Build verification* — the LLM compiles the binary before calling any playbook
* *Deploy workflow* — three `ansible-playbook` calls, in order, with named tasks

[TIP]
====
The Dockerfile template in `AGENTS.md` uses `WORKDIR /tmp/build` and `-buildvcs=false`. These are
not arbitrary choices — they work around specific constraints of the `ubi9/go-toolset` image and
Tekton's git-clone workspace. If you adapt this template for another language, apply the same level
of precision.
====

== Step 2: Understand the Ansible playbooks

Open each playbook and read the task names — they read like a runbook:

[source,sh,role=execute]
----
cat scripts/git-push.yml
----

[source,yaml]
----
tasks:
  - name: Remove existing origin remote
  - name: Create repository on Git server
  - name: Configure git identity
  - name: Stage all files
  - name: Commit if there are staged changes
  - name: Push to Git server
  - name: Get repository URL
  - name: Print result
----

[source,sh,role=execute]
----
cat scripts/build-image.yml
----

[source,yaml]
----
tasks:
  - name: Get repository URL
  - name: Create build project
  - name: Grant pipeline service account registry-editor role
  - name: Apply Tekton Pipeline and workspace PVC
  - name: Trigger PipelineRun
  - name: Wait for PipelineRun to succeed (up to 15 min)
  - name: Assert PipelineRun succeeded
  - name: Print built image reference
----

[source,sh,role=execute]
----
cat scripts/gitops-deploy.yml
----

[source,yaml]
----
tasks:
  - name: Get repository URL
  - name: Create dev project
  - name: Allow dev namespace to pull images from build namespace
  - name: Update image reference in deployment manifest
  - name: Commit and push updated manifest
  - name: Deploy developer-owned Argo CD instance
  - name: Wait for Argo CD instance to become Available
  - name: Create Argo CD Application
  - name: Wait for application to sync and become Healthy
  - name: Show application URLs
----

[NOTE]
====
The Argo CD instance in `gitops/base/argocd.yaml` belongs to the *developer*, not the platform.
The `openshift-gitops-operator` (installed in the previous lab) allows any user to create an
`ArgoCD` CR in their own namespace — no cluster-admin access required.
====

== Step 4: Verify the in-cluster LLM is registered in Dev Spaces

OpenCode is **not** installed from the template. Dev Spaces 3.29 injects it from the AI tool registry applied with `deploy/instances` in Lab 1.4. The same apply mounted `opencode.json` so every workspace talks to Qwen3.8.

[source,sh,role=execute]
----
CHE_NS=$(oc get checluster -A -o jsonpath='{.items[0].metadata.namespace}')

echo "CheCluster namespace: $CHE_NS"

oc get configmap ai-tool-registry -n "$CHE_NS" \
  -o jsonpath='{.data.registry\.json}' | python3 -m json.tool

oc get configmap opencode-workspace-config -n "$CHE_NS" \
  -o jsonpath='{.data.opencode\.json}' | python3 -m json.tool
----

You should see:

* Provider `opencodeai/opencode` with injector `quay.io/che-incubator/dashboard-ai/opencode:next`
* `defaultAiProviders` set so the dashboard AI Selector is pre-checked
* `baseURL` pointing at `https://maas.<apps-domain>/llm-serving/qwen3/v1`
* Provider and model **name** `Qwen3.8` (the API model id stays `qwen3` — that is what vLLM serves)
* `limit.output: 8192` so OpenCode does not request 32 000 tokens against `--max-model-len=40960`

[NOTE]
====
The AI provider feature is a Dev Spaces *Technology Preview*. The dashboard shows an **AI Provider** section on Create Workspace when `ai-tool-registry` exists. Developers do not paste an API key — Secret `ai-provider-openai-api-key` injects the MaaS `sk-oai-` key as `OPENAI_API_KEY`.
====

== Step 5: Adapt devfile.yaml — set your GIT_SERVER

The `devfile.yaml` has one value to update: the `GIT_SERVER` environment variable.
This is the URL of the in-cluster Git server where developers will push their application repos.

[source,sh,role=execute]
----
cat devfile.yaml | grep GIT_SERVER
----

Expected output:

[source,console]
----
        - name: GIT_SERVER
          value: https://gitpop.apps.sno.msl.cloud
----

Get your cluster's Git server URL and update the devfile:

[source,sh,role=execute]
----
GIT_SERVER=https://$(oc get route gitpop -n gitpop \
  -o jsonpath='{.spec.host}')

echo "Git server: $GIT_SERVER"

sed -i "s|https://gitpop.apps.sno.msl.cloud|${GIT_SERVER}|g" devfile.yaml
----

Commit and push the change to your fork:

[source,sh,role=execute]
----
git add devfile.yaml
git commit -m "fix: adapt GIT_SERVER for workshop cluster"
git push
----

[NOTE]
====
If you are using the shared workshop cluster with the pre-configured defaults, the values already match and no push is required. Share the DevSpaces URL directly from Step 6.
====

== Step 6: Share the developer launch URL

Developers open a single URL to get a fully configured workspace.
Construct it from your Dev Spaces instance and the template repository:

[source,sh,role=execute]
----
DEVSPACES_URL=$(oc get checluster -A -o jsonpath='{.items[0].status.cheURL}')

TEMPLATE_URL="https://github.com/fjcloud/go-app-template"

echo "============================================"
echo " Participant workspace URL:"
echo "  $DEVSPACES_URL/#$TEMPLATE_URL?ai-provider=opencodeai/opencode"
echo "============================================"
----

When a developer opens that URL, Dev Spaces:

1. Clones the template repository
2. Injects OpenCode from the AI tool registry (init container) and mounts `opencode.json` (Qwen3.8)
3. Runs `bootstrap` for gitpop and Ansible only
4. Opens a VS Code workspace with the three deploy tasks visible in the sidebar (rocket icon)

[TIP]
====
The *Tasks panel* in DevSpaces (sidebar → rocket icon) shows all `commands` from the devfile. Developers see:

* *1. Push code to Git server* — runs `ansible-playbook scripts/git-push.yml`
* *2. Build container image* — runs `ansible-playbook scripts/build-image.yml`
* *3. Deploy with Argo CD* — runs `ansible-playbook scripts/gitops-deploy.yml`

OpenCode generates the app. The developer triggers the tasks in order to ship it.
====

[IMPORTANT]
====
Workspaces created *before* the AI registry existed do not include the OpenCode injector.
Create a *new* workspace from the URL above — restarting an old workspace is not enough.
====
