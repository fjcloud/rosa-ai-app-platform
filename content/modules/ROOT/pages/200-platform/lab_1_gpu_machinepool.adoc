= Lab 1.1 — Deploy a GPU Machine Pool

Add one NVIDIA L40S worker to your existing ROSA hosted control plane (HCP) cluster. It will run the workshop's model.

[NOTE]
====
*Estimated time:* 15–20 minutes, mostly provisioning. Create the pool now, then continue to the next lab.
====

== Create the GPU pool

Run these commands in the bastion terminal from Act 0. They use the cluster you are logged in to and reuse an existing worker subnet. No cluster name or availability zone needs replacing.

[source,sh,role=execute]
----
CLUSTER=$(oc get infrastructure cluster \
  -o jsonpath='{.status.infrastructureName}')
SUBNET=$(rosa list machinepools --cluster "$CLUSTER" -o json |
  jq -er '.[0].subnet')
rosa list machinepools --cluster "$CLUSTER"
----

If `gpu` already exists with type `g6e.xlarge` and one desired replica, skip creation and continue to the next lab. Otherwise, create it:

[source,sh,role=execute]
----
rosa create machinepool \
  --cluster "$CLUSTER" \
  --name gpu \
  --replicas 1 \
  --instance-type g6e.xlarge \
  --subnet "$SUBNET" \
  --taints 'nvidia.com/gpu=present:NoSchedule' \
  --yes
----

The `g6e.xlarge` instance has one NVIDIA L40S GPU. The taint reserves it for workloads that explicitly tolerate `nvidia.com/gpu=present:NoSchedule`.

[IMPORTANT]
====
The node incurs AWS charges while running. Keep this pool at one node for the workshop. The account needs at least 4 available *Running On-Demand G and VT instances* vCPUs in the cluster's region, and `g6e.xlarge` must be available in the selected subnet's zone.
====

.Optional: use Spot for the GPU worker
[%collapsible]
====
Use a current ROSA CLI with HCP Spot support (tested with https://github.com/openshift/rosa/releases/tag/v1.2.66[1.2.66]) and a cluster version that enables Spot. Add `--use-spot-instances` to the creation command above. Choose Spot when creating the pool; an existing pool cannot be converted in place.

Spot uses the separate *All G and VT Spot Instance Requests* quota; this worker needs 4 available vCPUs. The default maximum price is the on-demand price. AWS can reclaim the node, interrupting model serving; GPU capacity is still required. See the https://docs.redhat.com/en/documentation/red_hat_openshift_service_on_aws/4/epub/install_clusters/rosa-hcp-config-aws-spot-instances-cli[Red Hat Spot guide].

Verify that Spot was actually enabled:

[source,sh,role=execute]
----
rosa describe machinepool --cluster "$CLUSTER" --machinepool gpu -o json |
  jq -e '.aws_node_pool.spot_market_options != null'
----

The result must be `true`. ROSA CLI 1.2.53 ignores the Spot flag for HCP pools. With CLI 1.2.66, the supplied 4.19.49 environment explicitly rejected Spot with `Spot Market Options are not allowed for this version`. Use an environment with Spot support before choosing this option.
====

== Check the request

[source,sh,role=execute]
----
rosa list machinepools --cluster "$CLUSTER"
----

Look for `gpu` with instance type `g6e.xlarge` and one desired replica. `0/1` means the node is still provisioning; `1/1` means it has joined.

[NOTE]
====
`InstanceLimitExceeded` or `VcpuLimitExceeded` means the facilitator must increase the regional GPU quota. `InsufficientInstanceCapacity` means AWS cannot currently supply the GPU in this zone. Ask the facilitator to select another existing worker subnet supported by the cluster; changing only `--availability-zone` does not select an HCP worker subnet.
====

.Facilitator: use another zone when GPU capacity is unavailable
[%collapsible]
====
If the VPC has no private subnet in a zone with GPU capacity, prepare one:

[source,sh,role=execute]
----
read -rp 'Availability zone with GPU capacity: ' GPU_ZONE
SUBNET=$(bash scripts/prepare-gpu-subnet.sh "$GPU_ZONE")
----

Choose a zone in the cluster's region, such as `us-east-1a` for a `us-east-1` cluster. The helper creates a free `/24` subnet in the existing VPC, tags it for this cluster, and reuses the worker subnet's NAT route. Repeating it reuses that subnet. It does not reserve GPU capacity.

If the new `gpu` request failed before any node joined, delete that empty request:

[source,sh,role=execute]
----
rosa delete machinepool --cluster "$CLUSTER" --machinepool gpu --yes
----

Run the creation command above again, keeping the new `SUBNET` value.

After the workshop, delete the GPU pool and wait for its instance and ROSA PrivateLink interfaces to be removed. Then remove the additional subnet:

[source,sh,role=execute]
----
aws ec2 delete-subnet \
  --region "$(oc get infrastructure cluster -o jsonpath='{.status.platformStatus.aws.region}')" \
  --subnet-id "$SUBNET"
----

Only remove the subnet returned by `prepare-gpu-subnet.sh`; the original worker subnet belongs to the base environment.
====

== Checkpoint

The `gpu` pool has been requested. Continue to *Lab 1.2 — Install Operators* while ROSA provisions the node. Lab 1.3 checks node readiness before deploying the model.

See the https://docs.redhat.com/en/documentation/red_hat_openshift_service_on_aws/4/html/cluster_administration/managing-compute-nodes-using-machine-pools[ROSA machine-pool documentation] for the available options.
