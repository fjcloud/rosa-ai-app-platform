== What is OpenShift AI?

Red Hat OpenShift AI (formerly RHODS) is a platform for building and serving AI-powered applications on OpenShift. This workshop uses a focused subset:

[cols="1,2", options="header"]
|===
| Component | Role

| *RHOAI Operator*
| Lifecycle of OpenShift AI components (`DataScienceCluster` / `DSCInitialization`)

| *DataScienceCluster*
| Enables subsystems. You turn on KServe, Models-as-a-Service (`aigateway.modelsAsAService`), the dashboard, and OGX (Gen AI studio).

| *KServe `LLMInferenceService`*
| The LLM serving API. One object is one model: GPU placement, vLLM, Gateway HTTPRoute.

| *Models-as-a-Service*
| Catalog (`MaaSModelRef`), access (`MaaSAuthPolicy`), quota (`MaaSSubscription`), and `sk-oai-` API keys.

| *Red Hat Connectivity Link*
| Authorino validates keys; Limitador enforces token windows. Required by MaaS.
|===

== The Model Serving Architecture

[source]
----
 Platform Engineer
        │
        ▼
 LLMInferenceService  +  MaaSModelRef / MaaSAuthPolicy / MaaSSubscription
        │  "Serve Qwen3.8 with Red Hat vLLM on GPU, publish through MaaS"
        ▼
 Gateway  maas.<apps-domain>  (Authorino + Limitador)
        │
        ▼
 Predictor Pod (GPU node)
        │  vLLM process, weights on PVC, TLS to the mesh
        ▼
 POST /v1/chat/completions   (OpenAI-compatible, Authorization: Bearer sk-oai-...)
----

The key insight: *one governed OpenAI-compatible front door*. LangChain, OpenCode, curl — anything that speaks OpenAI — works. One `sk-oai-` API key (not an access/secret pair). The dashboard at `https://rh-ai.apps.<apps-domain>/` is where you browse the catalog and mint extra keys; GitOps still owns the serving stack.

== Why not a plain Deployment?

[cols="1,1,1", options="header"]
|===
| Feature | Standard Deployment | LLMInferenceService + MaaS

| GPU placement
| Manual toleration + node selector
| Same, plus KServe workload presets (TLS, shm, probes)

| Public API
| You wire a Route and hope
| Gateway + HTTPRoute attached to `maas-default-gateway`

| Auth / quota
| None
| API keys, groups, token windows, 429 when over budget

| Metrics
| Generic CPU/memory
| vLLM tokens/s + MaaS consumption per key
|===

== The OpenAI-Compatible API

[source,sh]
----
# Cloud OpenAI:
curl https://api.openai.com/v1/chat/completions \
  -H "Authorization: Bearer $OPENAI_KEY" \
  -d '{"model": "gpt-4o", "messages": [{"role": "user", "content": "Hello"}]}'

# MaaS on this cluster (same JSON shape). Path-based URL keeps model id "qwen3":
curl https://maas.<apps-domain>/llm-serving/qwen3/v1/chat/completions \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -d '{"model": "qwen3", "messages": [{"role": "user", "content": "Hello"}]}'
----

== Qwen3.8: The Model You Are Deploying

[cols="1,2", options="header"]
|===
| Property | Value

| Model family
| Alibaba Qwen3.8 (通义千问3.8) — a Chinese-developed, open-weight dense model, packaged by Red Hat AI

| Variant
| Qwen3.8-27B — 27B dense parameters (native vision-language model; this workshop uses text only)

| Quantization
| INT4 / W4A16 (`compressed-tensors`) — ~19.5 GB, fits on a single L40S

| Serving engine
| Red Hat vLLM CUDA 3.5.0 (vLLM 0.24) — `registry.redhat.io/rhaii/vllm-cuda-rhel9:3.5.0`

| Context window
| 262,144 tokens natively; this workshop serves **40,960** tokens (`--max-model-len=40960`)

| Special capability
| Thinking/reasoning mode (`--reasoning-parser=qwen3`) and tool calling (`--tool-call-parser=qwen3_coder`)

| HuggingFace ID
| `RedHatAI/Qwen3.8-27B-INT4`
|===

[TIP]
====
*Why Qwen3.8?* Red Hat AI publishes a vLLM-ready INT4 checkpoint of Qwen3.8-27B. It combines strong reasoning (plan agent) with strong code generation and tool calling (build agent) in a package that fits on a single GPU. OpenCode needs `--enable-auto-tool-choice` and `--tool-call-parser=qwen3_coder`.
====
