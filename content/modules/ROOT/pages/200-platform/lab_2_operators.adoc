= Lab 1.2 — Install Platform Operators

Install the operators the coding-agent platform needs, from Kustomize in this repo — not by clicking OperatorHub. Reproducible, auditable, GitOps-friendly.

Trigger the apply and move on. Lab 1.3 waits for them before it publishes Qwen3.8.

[NOTE]
====
*Estimated time:* 5 minutes active + ~20 minutes background installation +
*Persona:* Platform Engineer +
*Fire and forget:* Trigger all installs, then move immediately to Lab 1.3 while they complete.
====

== What Gets Installed

Two groups, one `oc apply`. You do not configure any of these by hand — Lab 1.3 turns them on.

[cols="1,2", options="header"]
|===
| Group | Operators

| *Serve the model*
| OpenShift AI (KServe + MaaS + dashboard), NVIDIA GPU Operator, Node Feature Discovery, Leader Worker Set, cert-manager, Red Hat Connectivity Link (API keys and token quotas)

| *Ship the app*
| Dev Spaces (cloud IDE), OpenShift GitOps (Argo CD), OpenShift Pipelines (Tekton)
|===

[TIP]
====
Developers deploy their own Argo CD instance inside their project namespace — they never touch `openshift-gitops`. Your only job here is to ensure the operators are available cluster-wide.
====

== Step 2: Check the installation requests

Take one snapshot, then continue to Lab 1.3 while OLM installs the operators:

[source,sh,role=execute]
----
oc get subscriptions -A
----

A Subscription confirms the installation request, not a Ready operator. Lab 1.3 performs bounded readiness checks before applying instances. No background polling loops are needed here.

== What is Happening Under the Hood

OLM (Operator Lifecycle Manager) resolves each `Subscription` against the operator registry, generates an `InstallPlan`, installs CRDs and RBAC, then deploys the operator pod:

----
Subscription → InstallPlan → CRDs → RBAC → Operator Pod → Succeeded
----

Each operator registers Kubernetes types you will use next: `LLMInferenceService`, `MaaSModelRef`, `CheCluster`, `ClusterPolicy`, `Kuadrant`.
