== The Key Insights

*1. ROSA makes GPU infrastructure a Platform Engineer concern, not a developer concern.*
A single `rosa create machine-pool` command provisions NVIDIA hardware on AWS. Developers never interact with EC2 or node selectors.

*2. OpenShift AI makes LLM serving a catalog item, not a project.*
`oc apply -k` deploying an `LLMInferenceService` plus MaaS CRs gives every team a governed OpenAI-compatible API — keys, quotas, and the same interface they already know.

*3. AGENTS.md shifts governance from documentation to code.*
Platform conventions encoded in a Markdown file are read and enforced by the LLM at generation time. The developer gets a compliant app without opening a checklist.

*4. The same LLM powers the developer inner loop.*
OpenCode uses Qwen3.8 to write the Fortune Cookie app. Qwen3.8 is a *platform* capability.

*5. Observability closes the loop.*
GPU utilization, token throughput, and TTFT are visible in the same console as all other cluster metrics. Token quotas on the MaaS gateway make consumption attributable.

== What We Did Not Cover (But You Can Explore)

* *LLM scale-out with llm-d:* This workshop pins one vLLM replica. OpenShift AI's path is *Distributed Inference with llm-d* on `LLMInferenceService`: vLLM engines, an inference gateway and scheduler, KV-cache-aware routing, and LeaderWorkerSet when the model spans GPUs or nodes. Replica count is still moved by *KEDA* (it owns the HPA). The scaling *signal* is the workload variant autoscaler (WVA) — KV cache (`vllm:kv_cache_usage_perc`) and queue (`vllm:num_requests_waiting`), not CPU or memory. WVA is Developer Preview in OpenShift AI 3.5.
* *Multi-environment GitOps:* Add `deploy/overlays/stage/` and `deploy/overlays/prod/` with Kustomize overlays; use separate Argo CD `Application` objects per environment
* *Webhook-triggered pipelines:* Add an `EventListener` + `TriggerBinding` to Tekton so `git push` triggers builds automatically
* *Application autoscaling:* Add an HPA to the Fortune Cookie `Deployment` to scale based on HTTP requests
* *Model fine-tuning:* OpenShift AI Data Science Projects support fine-tuning workflows on proprietary data using distributed training
* *ROSA HCP (Hosted Control Planes):* This workshop already runs on ROSA HCP. The pattern isolates the control plane from worker nodes for stronger multi-tenancy and faster cluster provisioning.
* *OpenShift Service Mesh:* Do not install OSSM 3 by hand on OpenShift 4.22 — this cluster uses the Gateway API (`openshift-default`). Istio remains optional for app-to-app mTLS later.
