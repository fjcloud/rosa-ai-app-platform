= Lab 3.1 — GPU and Token Metrics

Act 3 is required. You stood up an in-cluster coding agent this morning and spent the afternoon prompting it. Inspect GPU and token usage, then relate it to the provisioned infrastructure. These dashboards show activity, not an AWS invoice.

OpenCode requests and model loading create GPU activity. Fortune Cookie serves local strings and makes no inference calls at runtime; its HTTP traffic uses the app’s CPU and memory.

== Part 1: NVIDIA DCGM (Web Console dashboards)

. Open the OpenShift Web Console and stay in *Administrator*.
. Left nav: *Observe → Dashboards*.
. *Dashboard* dropdown: *NVIDIA DCGM Exporter Dashboard* (ConfigMap `nvidia-dcgm-exporter-dashboard` in `openshift-config-managed`).
. At the top of the dashboard, set:
** *Instance* — the GPU worker (the series labelled `NVIDIA L40S` / `exported_namespace=llm-serving`). There is no “instance type” filter; pick that instance, not a CPU worker.
** *GPU* — `0` (this workshop has one L40S).
. Time range: last few hours so you see model load *and* the OpenCode afternoon.

Read these four panels (those names are on the dashboard). The numerical ranges are illustrative, not pass/fail thresholds; record what your cluster shows:

[cols="1,2,2", options="header"]
|===
| Panel | What it tells you | What you should see

| *GPU Utilization*
| Compute cores. High during OpenCode prompts, near 0 when idle.
| Idle ≈ 0%. During OpenCode bursts, 30–95%.

| *GPU Framebuffer Mem Used*
| VRAM: Qwen3.8 weights + KV cache on the 48 GiB L40S.
| Once the model is Ready, typically ~35–42 GiB (not the 19.5 GiB checkpoint alone).

| *GPU Temperature*
| Check temperature changes during model activity.
| Idle ~45–55°C; keep it under 80°C.

| *GPU Power Usage*
| Instantaneous power draw; AWS bills the VM for provisioned time, not a separate DCGM electricity meter.
| Idle ~90–120 W; under load up to ~300 W.
|===

On *GPU Utilization* over the last few hours you should see:

* A spike when weights loaded into VRAM
* Bursts when you used OpenCode (plan, build, change)
* Idle valleys between prompts — the GPU is not at 100% when nobody is chatting

[TIP]
====
If 50 developers used OpenCode all day, what would this graph look like? When would you add a second GPU node? That is how the platform team justifies expanding the machine pool.
====

== Part 2: vLLM tokens (Web Console metrics)

There is no separate “model metrics” page in OpenShift AI for this stack. Use the same console.

. Left nav: *Observe → Metrics*.
. Clear any sample query. Paste *one* expression below into the query box.
. Click *Run queries*. Set the time range to the last hour (or the afternoon).
. Repeat for each query (add a query with *Add query*, or replace the box).

Names use a *colon* (`vllm:generation_tokens_total`), not an underscore. Namespace is `llm-serving`.

[cols="1,2", options="header"]
|===
| Paste this | What you should see

| `rate(vllm:request_success_total{namespace="llm-serving"}[5m])`
| Successful completions. `finished_reason="stop"` is the normal path.

| `rate(vllm:generation_tokens_total{namespace="llm-serving"}[5m])`
| Decode throughput. On this L40S, typically 20–60 tokens/sec while OpenCode is answering.

| `histogram_quantile(0.95, rate(vllm:time_to_first_token_seconds_bucket{namespace="llm-serving"}[5m]))`
| p95 time-to-first-token. Compare it across prompts and load; long inputs and reasoning can increase latency.

| `vllm:num_requests_running{namespace="llm-serving"}`
| In-flight requests. 0 when idle.

| `vllm:num_requests_waiting{namespace="llm-serving"}`
| Queued requests; sustained waiting can indicate capacity pressure. This workshop has one fixed replica and no autoscaler.
|===

If a query returns *No datapoints*, stay in *Administrator* → *Observe → Metrics* (not the Developer perspective) and confirm `LLMInferenceService/qwen3` is Ready. User-workload monitoring is already on.

== Part 3: Token quota (OpenShift AI dashboard)

Graphs above are *usage*. The MaaS subscription limits consumption to 5 000 000 tokens / 24h. Over quota the gateway returns HTTP 429. This does not stop or scale down the GPU VM, which continues to incur charges.

. In the OpenShift Web Console, open the *Application launcher* (the grid) → *Red Hat OpenShift AI*, or use the dashboard URL printed in Lab 1.3.
. Log in with the same cluster user as `oc`.
. Open *Gen AI studio → AI asset endpoints*. Confirm *Qwen3.8* is *Ready*.
. Open *Gen AI studio → API keys* and select the *Subscriptions* tab. Open *Qwen3.8 workshop subscription* to see its *5 000 000 tokens / 24h* limit and active `workshop-opencode` key. Extra keys can be minted here; they do not replace the Dev Spaces Secret.

Confirm the same objects from a terminal if you want:

[source,sh,role=execute]
----
oc get maasmodelref -n llm-serving
oc get maasauthpolicy,maassubscription -n models-as-a-service
oc get tokenratelimitpolicy -n llm-serving
----

You should see `MaaSModelRef/qwen3`, `MaaSAuthPolicy/qwen3-access`, `MaaSSubscription/qwen3-workshop`, and a Kuadrant `TokenRateLimitPolicy` derived from the subscription. Auth only → 429 (no quota). Subscription only → 403 (no gateway access). Both are required.

Back in *Observe → Metrics*, the afternoon’s token count:

[source,promql]
----
sum by (namespace) (increase(vllm:generation_tokens_total{namespace="llm-serving"}[1h]))
sum by (namespace) (increase(vllm:prompt_tokens_total{namespace="llm-serving"}[1h]))
----

Prompt tokens are usually much larger than generation tokens (OpenCode sends `AGENTS.md` and the conversation). That is expected.

== Part 4: Relate usage to cost

Unlike a managed pay-per-token endpoint, this model runs on a fixed GPU worker. The bill includes VM uptime, ROSA worker charges, storage and any applicable networking charges. CPU workers and the Fortune Cookie application also use infrastructure. Check the current regional prices and your lab’s billing terms with the facilitator.

For illustration, if a GPU VM costs $2/hour and runs for four hours, its VM-only cost is $8 whether OpenCode is busy or idle. If it produced 100 000 output tokens in that period, the allocated VM-only cost would be $80 per million output tokens. That is a retrospective allocation, not a per-token price or a benchmark.

Use token quotas to manage fair access. Use worker lifecycle and capacity planning to manage infrastructure spend. Aggregate vLLM counters do not identify individual developers; per-user chargeback needs identity-linked usage records.

[cols="1,2", options="header"]
|===
| Capability | Mechanism

| Subscription token quotas
| `MaaSSubscription` → Kuadrant `TokenRateLimitPolicy`

| Self-service API keys
| OpenShift AI dashboard

| Usage tracking
| vLLM `vllm:generation_tokens_total` / `vllm:prompt_tokens_total` in *Observe → Metrics*

| Chargeback
| Usage allocation reconciled with actual cloud billing; not provided automatically by these graphs
|===

== Facilitator cleanup after everyone finishes

Keep shared inference available until all participants have completed their coding and deployment tasks. Participants should export any code they want to keep before the RHDP assignment expires.

For an assignment dedicated to this workshop, the facilitator can remove the model and its cache, then the GPU pool, from the *bastion terminal*. This stops coding inference; the Fortune Cookie app can still serve its existing messages.

[source,sh,role=execute]
----
cd "$HOME/rosa-ai-app-platform"
oc delete -k deploy/inference
CLUSTER=$(oc get infrastructure cluster -o jsonpath='{.status.infrastructureName}')
rosa delete machinepool --cluster "$CLUSTER" --machinepool gpu --yes
----

Wait for the pool and EC2 instance to disappear, and check storage cleanup in AWS. If you created an additional subnet, follow the scoped removal in Lab 1.1 after PrivateLink interfaces are gone. Keep the base cluster, original CPU pools and shared platform operators; RHDP manages the environment’s expiration. Do not run the E2E platform teardown script on a shared cluster.
