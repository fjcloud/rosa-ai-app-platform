== Part 1: NVIDIA DCGM

. In the OpenShift Web Console: *Observe → Dashboards*
. Dashboard dropdown: `NVIDIA DCGM Exporter Dashboard`
. Node filter: the `g6e.xlarge` GPU node

[cols="1,2,1", options="header"]
|===
| Metric | What it tells you | Healthy range

| *GPU Utilization %*
| Compute cores active. High during OpenCode prompts, near 0 when idle.
| 30–95% during load

| *GPU Memory Used (GiB)*
| Weights + KV cache. Qwen3.8-27B INT4 uses ~20 GB of 48 GB.
| ~20–40 GiB

| *GPU Temperature (°C)*
| L40S throttles above 87°C.
| < 80°C

| *GPU Power Draw (W)*
| Correlates with inference load — this is the electricity line on the bill.
| 50–300 W
|===

On the *GPU Utilization* graph for the last few hours you should see:

* A spike when weights loaded into VRAM
* Bursts when you used OpenCode (`/plan`, `/build`, the audit)
* Idle valleys between prompts — the GPU is not spinning at 100% when nobody is chatting

[TIP]
====
If 50 developers used OpenCode all day, what would this graph look like? When would you add a second GPU node? That is how the platform team justifies expanding the machine pool.
====

== Part 2: vLLM metrics

*Observe → Metrics*. Try:

[source,promql]
----
rate(vllm:request_success_total{namespace="llm-serving"}[5m])
----

[source,promql]
----
rate(vllm:generation_tokens_total{namespace="llm-serving"}[5m])
----

Qwen3.8-27B INT4 on this L40S is typically 20–60 tokens/sec depending on batch and prompt length.

[source,promql]
----
histogram_quantile(0.95,
  rate(vllm:time_to_first_token_seconds_bucket{namespace="llm-serving"}[5m])
)
----

95th percentile time-to-first-token should stay under 2–3 seconds for interactive use.

[source,promql]
----
vllm:num_requests_running{namespace="llm-serving"}
vllm:num_requests_waiting{namespace="llm-serving"}
----

When `num_requests_waiting` is consistently > 0, the model is saturated. This workshop is a fixed single GPU; production would use KEDA on that metric.

== Part 3: Token quota is how you cap cost

Lab 1.3 created the subscription. Open `https://rh-ai.apps.<apps-domain>/` or inspect with `oc`.

* `MaaSAuthPolicy/qwen3-access` — `system:authenticated` may call Qwen3.8
* `MaaSSubscription/qwen3-workshop` — *5 000 000 tokens / 24h* (workshop-generous)
* Kuadrant `TokenRateLimitPolicy/maas-trlp-qwen3` — generated from the subscription
* `sk-oai-` keys bound to that subscription

Auth only → HTTP 429 (no quota). Subscription only → HTTP 403 (no gateway access). Both are required.

[source,sh,role=execute]
----
oc get maasmodelref -n llm-serving
oc get maasauthpolicy,maassubscription -n models-as-a-service
oc get tokenratelimitpolicy -n llm-serving
----

[source,yaml]
----
apiVersion: maas.opendatahub.io/v1alpha1
kind: MaaSSubscription
metadata:
  name: qwen3-workshop
  namespace: models-as-a-service
spec:
  priority: 10
  owner:
    groups:
      - name: system:authenticated
  modelRefs:
    - name: qwen3
      namespace: llm-serving
      tokenRateLimits:
        - limit: 5000000
          window: 24h
----

[source,promql]
----
sum by (namespace) (increase(vllm:generation_tokens_total[1h]))
sum by (namespace) (increase(vllm:prompt_tokens_total[1h]))
----

Rough cost model for this L40S (~$1.65/hr on-demand, ~43 tok/s decode):

[source]
----
Cost/token           ≈ $0.000011
OpenCode session     ≈ 50 000 tokens → ~$0.55
10 concurrent devs   ≈ 500 000 tokens → ~$5.50 / hour of chatting
----

The Fortune Cookie route is not on this invoice. Token quota on the MaaS gateway is how you stop an afternoon of `/build` from becoming an unbounded GPU bill.

[cols="1,2", options="header"]
|===
| Capability | Mechanism

| Per-group token quotas
| `MaaSSubscription` → Kuadrant `TokenRateLimitPolicy`

| Self-service API keys
| Dashboard or `POST /maas-api/v1/api-keys`

| Usage tracking
| vLLM token counters + Limitador

| Chargeback
| Prometheus → cost model → cloud billing
|===
